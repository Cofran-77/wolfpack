# Visibility and community growth plan

[简体中文](GROWTH.md) | [Project home](../README.en.md)

The goal is successful installation and repeat use by people who need a captain to decide, CLI workers to execute, and code to verify. Stars are a useful endorsement signal, not a guaranteed outcome or a substitute for adoption. This is a proposed plan; no outreach or partnership is implied.

## Positioning and evidence

One sentence: **Wolfpack connects an AI captain, selectable CLI workers, and mechanical acceptance; DSH adds native controls and a live sidebar, with Codex and MCP editions available too.**

Keep the comparison, install entries, bilingual manuals, architecture, tests, and known limits prominent. Record a real 45–90 second DSH demo: enable → choose worker → delegate a reproduced small problem → show verification and sidebar. Use actual runs and remove personal paths, sensitive task content, and account details. Add a Universal CLI example so users without DSH can understand the core workflow.

Performance claims need reproducible tasks, starting/ending commits, OS, CLI/model versions, acceptance commands, elapsed time, usage evidence, and retries. Compare direct and delegated execution on the same task and standard. Convert costs using actual provider rates; do not assume “90% savings.”

## A 30-day experiment

| Time | Action | Evidence to collect |
| --- | --- | --- |
| Week 1 | Real demo and first-success tutorial; invite 3–5 relevant testers | Install friction, time to first pass, edition-selection confusion |
| Week 2 | Share focused cases in suitable DSH/Codex/MCP communities; consider Show HN or relevant Reddit posts under their rules | Qualified visits, attempted installs, feedback by channel; no repetitive posts |
| Week 3 | Apply to appropriate MCP directories/awesome lists; organize genuine support requests | Directory eligibility, working links, relevant audiences |
| Week 4 | Ship maintenance based on feedback; share an authorized user case | Response quality, improved first success, repeat usage, channel effectiveness |

DSH audiences need native interaction; Codex audiences need task specifications, six tools, and independent verification; MCP audiences need portable entry points. Each post should explain one concrete problem with reproducible steps and a repository link. Topics and descriptions improve discovery but cannot replace usefulness.

## Measure adoption

Track available weekly traffic/clone data, voluntary install feedback, first successful acceptance, repeat use, and star changes. Export GitHub traffic periodically within the platform's available window. Do not add hidden telemetry. Use a visits → install → first pass → return/recommend funnel, rather than counting every visit as a user.

Experiment targets can be “remove the top three installation obstacles” or “help five newcomers complete a verifiable task.” Never promise thousands of stars by a date. Invite a star naturally when useful. No purchased stars, exchanges, mass unsolicited messages, or fabricated testimonials.

## Maintenance

Use bilingual issue templates for edition, host, worker, and reproduction evidence. Mark only real, confirmed, bounded tasks with clear acceptance criteria as good first issues. Reproduce reports, communicate impact and next steps, and release meaningful improvements rather than empty activity.

Priority: **real demo and first success → focused community cases → reproducible comparisons and feedback → sustained maintenance**. Social publishing, directory submissions, and contacting users remain future actions; this delivery prepares repository materials and the plan only.
