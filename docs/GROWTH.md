# 曝光与社区增长计划

[English](GROWTH.en.md) | [项目首页](../README.md)

目标是让需要“队长判断、CLI 工人执行、机械验收”的用户真正装起来并持续使用。Stars 是认同信号，不能保证数量，也不能代替安装成功率和留存。以下为待执行计划，未代表已发布推广内容或已取得合作。

## 定位与展示

对外一句话：**Wolfpack 把 AI 队长、可选 CLI 工人和代码验收接起来；DSH 提供原生开关与实时面板，Codex/MCP 用户也能接入。**

首页保留三版对比、安装入口、双语手册、架构、测试与已知边界。制作真实 45–90 秒演示：打开 DSH 开关 → 选择工人 → 派一个已复现的小问题 → 展示验收结果和面板。画面须来自真实运行，隐藏个人目录、任务内容与账户信息。再提供一个不依赖 DSH 的通用 CLI 示例，使不同用户快速理解核心价值。

性能内容需要可复现：公开任务、起始提交、目标提交、操作系统、CLI/模型版本、验收命令、总耗时、原始用量来源和返工次数。比较直接执行与委派时使用同一任务和标准；价格按实际供应商费率换算，不能预设“省 90%”。

## 30 天实验

| 时间 | 行动 | 检查标准 |
| --- | --- | --- |
| 第 1 周 | 完成真实演示与首次成功教程；让 3–5 位目标用户试装 | 记录安装卡点、首次 pass 时间、理解三版差异的难点 |
| 第 2 周 | 在合适的 DSH/Codex/MCP 社区发布技术案例；按各社区规则提交 Show HN 或相关 Reddit 帖 | 分渠道记录合格访问、实际试装和问题反馈；不要重复灌帖 |
| 第 3 周 | 向合适的 MCP 目录与 awesome 列表提交规范申请；整理真实支持需求 | 列表必须允许本类项目，链接有效，避免无关收录 |
| 第 4 周 | 发布基于真实反馈的维护更新；展示一个用户案例（获授权） | 问题响应、首次成功改善、回访使用，复盘哪些渠道有效 |

DSH 社区优先展示插件交互；Codex 社区优先展示任务书、六工具和独立验收；MCP 社区展示可移植入口。一次发布围绕一个具体问题与可复制步骤，开头解释适用对象，末尾提供仓库入口。仓库 topics 与简介帮助检索，不能代替内容与体验。

## 衡量效果

记录每周访问/clone 数据、可自愿分享的试装反馈、首次验收成功、复用与 Stars 的变化。GitHub 流量按平台实际可用窗口定期导出；不加入隐形遥测。使用“访问 → 试装 → 首次 pass → 复用/推荐”的漏斗解释流失，不把每个访问等同于真实用户。

实验目标可以是“找出前三个安装障碍并消除”“让五位新用户完成首个可验收任务”，不要许诺某天必达几千 Stars。README 中自然邀请有帮助的用户 Star，更新日志说明具体进步；不买星、不互刷、不群发、不创建伪造用户评价。

## 维护机制

双语 issue 模板收集版本、宿主、工人和复现证据。good first issue 只标已确认、范围明确、验收清楚的真实任务，例如补已验证工人的文档或可复现边界测试。收到反馈先确认复现与影响，给出下步或已知限制。按实际更新发布变更记录，避免为活跃度制造空更新。

优先级：**真实演示 + 首次成功教程 → 定向社区案例 → 可复现比较与用户反馈 → 持续维护**。推广帖、目录申请与用户联系需要另行实际执行；本次交付仅准备计划与仓库材料。
