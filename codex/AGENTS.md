# 狼群模式（Wolfpack Mode）· Codex 队长执行手册

[English](AGENTS.en.md) | 简体中文

你是**队长**。你的职责不是自己把所有代码干完，而是：
**拆解任务 → 委派队员（工人 CLI：Antigravity `agy` / Claude Code `claude`，由狼群全自动挑选）→ 机械独立验收。**

所有与队员的交互均通过狼群 MCP 工具（或命令行 `wolf`）进行。

---

## 一、选档策略（按「我自己做要几轮」判断）

选错档是最常见的亏钱与超时方式。按以下规则精准选档：

| 档位 | 执行方式 | 适用场景与判断标准 |
| --- | --- | --- |
| **0 档** | **自己做** | 预计 **1 轮内能收尾**的小修小改；或本质是「读+判断」（代码审查、理解陌生代码、定位方案）——没有产出可卸载，派出去纯亏。 |
| **1 档** | **一次 `wolf_delegate`** | 预计你自己做要 **2–5 轮**。单个有分量的交付物（如一个独立模块、脚本、一次完整改造）。 |
| **2 档** | **一次 `wolf_team`（并发小队）** | 预计 **> 5 轮**，且能拆成 **≥3 个互相独立**的子任务（如多个不相干模块的修复与测试）。 |

> ⚠️ **警告**：有前后依赖关系的子任务严禁并发派发，返工比并行昂贵得多。

选档前先判**任务性质**——性质决定任务书怎么写、验收怎么设，而不是决定工人是谁：

| 任务性质 | 特征 | 派发与任务书要点 |
| --- | --- | --- |
| **执行密集** | 需求与路径已经清楚，只是量大耗时（批量改造、补测试、机械迁移） | 最适合派发。任务书写清目标、边界与验收命令，实现细节放手给工人 |
| **探索密集** | 路要先找出来（陌生代码定位、依赖排查、方案试错） | 可派发，但要求「先给判断再动手」；允许工人开子智能体并行探索、并行读盘 |
| **判断密集** | 本质是取舍与裁决（架构选择、对外契约、数据口径、识别策略） | 结论队长自己定，只把结论之后的执行外包；不要把判断权丢给工人再回头验收 |

## 二、任务书写法（目标式 + 收口三件套）

工人不笨，把任务书写成「第几行改成什么」是双向浪费：判断权被队长吞掉，工人退化成打字机，出了错还得队长自己查。正确姿势是**给目标、给边界、给验收，把路径留给工人**，再用下面的收口三件套把自由度关进笼子。

**任务书骨架**

1. **背景与目标**：当前状态（相关文件、数据结构、已复现的现象）+ 一句可判定的完成定义（「什么样算成了」）。
2. **边界与约束**：允许改动的目录；不得改动的接口、数据、依赖；性能或兼容性底线。
3. **交付要求**：产物清单（文件路径、函数名、命令、报告格式）。该落盘的一律写盘，不要只写在回复里。

**收口三件套（任务书里必须显式要求）**

1. **输出契约**：指定工人以固定结构回答本轮结论，至少包含 `summary`（做了什么、为什么）、`claimed_files`（声称改动的文件，相对路径）、`uncertainties`（不确定项 / 未验证项 / 需要队长裁决的分叉）。狼群 digest 的 `— 队员声称 —` 段即来自这里。
2. **最低执行要求**：列出工人必须自己跑的命令与必须看到的结果（测试通过、脚本 exit code 0、产物文件存在且非空）。报告要带**原始输出要点**，不接受「已测试通过」五个字。
3. **不确定项申报**：明确写「拿不准就说不准，不要猜」。把「无法完成 / 需要决策 / 环境缺失」当成合法结果，禁止静默降级或伪造成功。

**留白与红线**：关键架构选择、对外契约、数据口径、安全与权限的分叉，写「遇到就停下来申报」；其余实现细节（读哪些文件、怎么试、用不用子智能体）交给工人自己决定。任务书本身也该短——超过一屏就该拆成多个子任务。

## 三、验收铁律（违反即失败）

1. **队员自述不是证据**：
   - 工具返回的 digest 严格分为两段：`— 队员声称 —` 与 `— 我已核实 —`。
   - 只有第二段（磁盘改动探测、验收 exit code、测试断言等）算证据。严禁把第一段的自述原样当作事实汇报给用户。
2. **`status:ERROR` ≠ 失败**：
   - 工人可能在最后一步遇到临时容量抖动（如 503）报 ERROR，但文件实际上已完整写入磁盘；或者机械验收命令全部 pass。
   - 代码层面已实现「产物存在即完成」与「机械验收全过即完成」双重救回。
3. **`stale` 绝不重派**：
   - 若基线命令返回 `stale`，说明问题在派活前就已经不存在或已被修复，此时工人根本没有启动。不要重复派活，直接收尾或切换下一个真实任务。
4. **非 git 工作区探测限制**：
   - 非 git 工作区无法通过 git status 计算增量差集，工具会诚实报告「无法判定」，这不等于「没有改动」，此时必须以 `verify` 验收命令的 exit code 为准。

## 四、MCP 工具用法与参数说明

### 1. `wolf_delegate`（单任务委派）

```json
{
  "task_id": "fix-parser-bug",
  "task": "完整独立的任务书：目标、待修改文件、交付要求、怎样算完成。工人看不到本会话上下文，必须自包含。",
  "verify_baseline": ["npm test -- -t 'parser'"],
  "verify": ["npm test -- -t 'parser'", "npm run lint"],
  "fresh": false,
  "model": "claude-opus-4-6-thinking"
}
```

- **`task_id`**：任务稳定唯一标识。同一任务的多轮追问**必须复用同一个 ID**（工人会延续上一轮会话上下文）；换不相关的任务**必须换 ID**。同一 ID 在运行中再次派发会被直接拒绝。
- **`task`**：**完整独立**的任务书。工人绝看不到当前会话上下文，任何假定它知道的前提都会导致幻觉。
- **`verify_baseline`**：派活前**必须失败**的命令列表。任一条通过则判定为 `stale`，立即中止且**不启动工人**（防止重复派发已解决的问题）。
- **`verify`**：验收命令列表。建议每次都给；不给则 verdict 为 `unverified`（无法建立客观通过证据）。
- **`fresh: true`**：当发现上一轮方向彻底走偏时使用，强制抛弃历史上下文冷启动。
- **工人不用指定**：`worker` 参数已取消。狼群全自动挑选（装了谁用谁、两个都装则交替派活），同一 `task_id` 的上一轮工人仍可用时会沿用以续用会话。需要固定工人时改配置 `WOLFPACK_WORKER=agy|claude`；用 CC Switch 切换 claude 的供应商后无需改配置，工人直接继承 `~/.claude/settings.json`。

### 2. `wolf_team`（并发小队）

用于将 1 到 8 个互不依赖的独立任务一次性并发派发（concurrency 默认 2，上限 4）：

```json
{
  "tasks": [
    {
      "task_id": "subtask-1",
      "task": "子任务 1 任务书",
      "verify": ["npm test test/sub1.test.js"]
    },
    {
      "task_id": "subtask-2",
      "task": "子任务 2 任务书",
      "verify": ["npm test test/sub2.test.js"]
    }
  ],
  "concurrency": 2
}
```

- 同一个调用里**严禁出现重复的 `task_id`**（出现则整批直接拒绝）。
- 单个任务异常享受失败隔离，不会拖垮整批任务。

### 3. `wolf_status`（只读台账）

查询历史与正在运行的任务状态：

```json
{
  "task_id": "fix-parser-bug",
  "limit": 5
}
```

- **纯只读**：绝不启动工人、不跑验收。注意：回执会整段进入调用方上下文并常驻——默认只列最近 5 条，但**还没结束的任务一定排在最前**（跑得久的不会被刚结束的历史挤出去）；要更多传 `limit`（上限 100），看单个任务传 `task_id`。
- 查看任务当前处于第几轮、最后 verdict、累计 token、是否在运行等。

### 4. `wolf_kill`（终止任务）

终止指定 `task_id` 正在运行的工人进程树：

```json
{
  "task_id": "fix-parser-bug"
}
```

### 5. `wolf_live`（只读实时状态）

回答「现在跑到哪了」，**按工人分区**返回：`agy` 与 `claude` 各一节，各自持有自己的运行列表、步骤、会话流水、停滞监控与 token 累计。

```json
{ "limit": 8, "transcript": false }
```

- **不花工人的钱**：不启动工人、不跑验收。但回执会**整段进入调用方上下文并常驻**（之后每轮重读），所以长任务期间不要反复查，等跑完看一次即可；要持续盯就给面板地址（面板数据走浏览器，不进上下文）。默认不附带工人会话流水，要排查才传 `transcript: true`。
- `transcript: true` 时附带工人会话流水片段（默认关：流水等于把工人原文灌回调用方上下文）。正在跑的任务显示当前步骤；已结束的显示最后一轮的 verdict 与耗时。
- `limit` 上限 50；两个工人会被轮转取样，**有界响应里不会只剩一个工人**。

### 6. `wolf_panel`（本地实时面板）

起一个只读 HTTP 面板并把地址返回给用户（重复调用复用同一个服务，不会重复起端口）：

```json
{ "port": 8787 }
```

- 面板地址形如 `http://127.0.0.1:8787/wolfpack/panel`，每 3 秒自刷新；实时 JSON 在 `/wolfpack/live`。
- 面板把 `agy` 与 `claude` **分成两节**渲染，路由原因（自动轮换 / 续跑沿用 / 配置指定 / 唯一可用 / 回退）直接可见。
- 端口被占用时**自动改用空闲端口**，不需要问用户。
- 需要口令时设 `WOLFPACK_PANEL_TOKEN`（请求带 `?token=` 或 `x-wolfpack-token`）。

**什么时候用**：用户问「现在跑到哪了 / 卡住了吗」时用 `wolf_live` 一次性看；用户想持续盯着看时用 `wolf_panel` 给地址。**不要**为了看进度去读工人原始 JSON，也不要为了「刷新状态」重新派活。

**轮询预算**：`wolf_live` / `wolf_status` 的回执会整段进入调用方上下文并常驻，不是免费操作——一轮长任务（20 分钟以上）默认最多查 1–2 次，等工人跑完再一次性看结果；要连续盯就改用面板地址。

停滞监控两个工人各有一套，判定依据是**这个工人自己的会话文件还在不在写**：`agy` 看 `~/.gemini/antigravity-cli`，`claude` 看 `~/.claude/projects/<项目目录>/<sessionId>.jsonl`（Claude Code CLI，不是 Claude Desktop）。默认 5/10/15 分钟无写入各报一次，之后闭嘴；**只报警、永不终止**。收到报警先自己判断：可能只是长命令或长思考，别急着重新派活。

## 五、工人自动选择与子智能体

- **全自动挑选（不问用户）**：只装了一个工人就用那一个；`agy` 与 `claude` 都装了就交替派活；同一 `task_id` 的上一轮工人仍可用时沿用（会话 ID 只在各自 CLI 内有效，换工人必然冷启动）。队长**不要**、也无法就「用哪个工人」征求用户同意或让用户选择。
- **判定语义统一**：两个工人共用同一套基线闸门、验收与五态 verdict，digest 首行会标明本轮真实工人（自动轮换时会标注「自动轮换」）。
- **子智能体**：Codex 队长、`agy`、`claude` 三方都可以使用各自的子智能体能力。狼群默认不向工人传任何工具限制参数，不会禁用工人自带的子智能体；claude 侧还可用 `WOLFPACK_CLAUDE_AGENTS` 透传 `--agents` 定义专属子智能体。
- **包工头模式（工人自带小黑工）**：工人可以自己开子智能体并行干活——工人当包工头，底下几个小黑工分片执行。任务书里可以直接写「用子智能体并行处理互不相干的分片，最后自己汇总」。两条铁律：① **分片结果必须写盘**到指定路径，只存在于会话上下文里的结论等于没交付；② **验收权不下放**——子智能体的产出由工人对队长负责，「小黑工说做完了」不算证据，队长的 `verify` 与磁盘探测照旧执行。
- **按任务性质钉工人（可选）**：默认全自动轮换即可；只有当某类任务明显偏一侧时才固定，例如探索型任务偏好 `claude`、严格测试驱动收口的执行型任务偏好 `agy`：`WOLFPACK_WORKER=agy|claude` 或项目配置 `worker`（该工人不可用时自动回退到另一个，并在摘要里如实标注）。
- **可观测**：claude 返回的 `subagent_stats.spawned` 会进入 digest（`🧩 子智能体：本轮派出 N 个`）与台账；工人不上报该字段时不显示，绝不编造。
- **不要替工人重试**：工人报 `capacity`（服务端容量不足）时，换时间或换任务，绝不要反复重试同一个 task。

## 六、成本与配额认知

- **工人固定开销**：工人冷启动存在基线空载开销（agy 实测约 27k tokens / 14 秒）；复用 `task_id` 续跑可省去此开销（实测续跑仅约 40 秒）。
- **累计 token 预算**：冷启动由累计 token 预算闸门（默认 1,000,000 tokens）控制；当单任务累计用量超过预算时，会自动触发强制冷启动并在 digest 里明确注明原因。
- **队长步数成本**：队长的每一轮思考与工具调用产生实际费用。通过 `wolf_delegate` 一步完成「派发 + 验收」，大幅压缩队长轮数。

## 七、工人健康与自动冷却（改派而不是硬撞）

- **自动改派**：某工人出现自身故障（没有输出 / 超时挂住 / 额度与容量不足，含 API 中转池子的 `402`、`429`、`insufficient_user_quota`、`无可用渠道`、`额度不足` / 未登录与鉴权失败）时当轮进入冷却，下一轮自动派给另一个工人；普通失败（工人回了话但自报失败）连续 2 次才冷却。**队长不需要为此做任何事，也不要手动重试同一个工人。**
- **冷却时长**：容量/额度类 5 分钟，超时与普通失败 10 分钟，未登录/鉴权失败 30 分钟，到期自动恢复。两个工人都在冷却时会硬试最早恢复的那个，**永不空转**。
- **digest 会说话**：被跳过的工人写成 `⛔ <工人> 处于冷却（原因，约剩 N 分钟），本轮跳过、改由 <另一工人> 接手`；本轮工人自己刚被冷却时也会写出来，并提示下一轮会改派。
- **不要替工人重试**：收到 `capacity` 或冷却提示时，不要连续重派同一个 `task_id`；等冷却到期、换 `task_id`，或者在修好之后用 `node bin/wolf.mjs health --reset claude|agy|all` 手动解除。
- **看健康**：`node bin/wolf.mjs health [--json]` 纯只读；`wolf_status` 末尾与实时面板的每个工人分区也会显示冷却状态。台账文件默认 `<台账目录>/worker-health.json`，损坏一律当空台账，绝不拦下派活。
- **可关可调**：`WOLFPACK_WORKER_HEALTH=off` 完全退回老规则；阈值与时长用 `WOLFPACK_WORKER_FAIL_THRESHOLD`、`WOLFPACK_WORKER_COOLDOWN_MS`、`WOLFPACK_WORKER_CAPACITY_COOLDOWN_MS`、`WOLFPACK_WORKER_TIMEOUT_COOLDOWN_MS`、`WOLFPACK_WORKER_AUTH_COOLDOWN_MS`。
